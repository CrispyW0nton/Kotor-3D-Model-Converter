## Headline goals (carried forward)

1. **Qt is the only supported front-end.** Tk frozen and removed by M3. ✅ Done.
2. **A real Character Builder window**, modeled on the AccuRig HUD, with **four model-type modes** matching KOTOR's actual asset classes: Headless Body, Head, Supermodel (Head + Headless composite), Creature.
3. **A truthful viewport** with joint-dot HUD, mini-thumbnail inset, snap-views, weight heat-map. ✅ Done in M4.
4. **A complete creature rigging path** — spline-IK chains, wing rigs, ROM tests — from the Stewart Jones playbook. **Pending — M8.**
5. **Validation banner + bottom strip** surfacing `validation_service.py` checks live. Plumbing exists; live debounce pending in M9.
6. **A modder-complete external mesh pipeline:** import OBJ/FBX/glTF, choose a known-good KOTOR skeleton/template from game data, adjust guides in the AccuRig-style HUD, preview KOTOR/supermodel animations, and export MDL/MDX that can be reloaded by GhostRigger/PyKotor. **This is now the launch gate.**
7. **A testable KOTOR Unity bridge:** repeatable MCP/game-data transfer into Unity, with animation/skinning validation for representative characters such as `n_darthmalak`.
8. **A full asset-preview workbench:** characters, heads, outfits, weapons/items on hooks, and animation playback without launching the game.
9. **Module and map authoring pillars:** module hydration/editing, walkmesh editing, LYT/VIS room layout, and safe `.mod` packaging.

## Launch-gap audit: custom model to playable KOTOR asset

The 2026-05-16 audit reframed the roadmap around the real modder question:

> Can someone import a custom OBJ/FBX, select a KOTOR skeleton/template, adjust the rig in an AccuRig-like HUD, preview KOTOR animations, and export a working MDL/MDX?

Current answer: **not yet**. The builder has a strong HUD and service scaffold, but four launch gaps remain.

| Gap | Current state | Roadmap owner | Launch acceptance |
|-----|---------------|---------------|-------------------|
| Real export | `QtExportDialog` exists, but `headless_body_workflow._export_single_format()` still returns `not_implemented` for KOTOR/FBX/glTF/OBJ | M10/T1001 | KOTOR export writes `.mdl` + `.mdx`; FBX/glTF/OBJ write real files; exported KOTOR file reloads through GhostRigger/PyKotor |
| Skeleton/template selection | `character_builder.load_template()` and `apply_template_rig()` exist, but the guided HUD lacks a "choose KOTOR skeleton/resref" step for imported meshes | M12/T1201-T1202 | User can pick K1/K2 + body/head template/resref from game data, apply it to an imported mesh, and see the selected skeleton overlaid before binding |
| Manual guide edits as rig input | Joint-dot hit-test/drag exists in `qt_viewport.py`, but edits are not yet a clearly persisted guide override feeding the next `generate_skeleton()` call | M12/T1203 | Dragging HUD joints updates guide data, survives undo/redo, and changes the generated skeleton |
| Animation assignment | Preview controls exist; Add Motions still routes to a future animation-library action | M12/T1204 + M9/T903 | User can attach or inherit a KOTOR supermodel animation set, preview idle/walk/talk/combat/ROM, and see export validation fail when required clips are missing |

## Product-pillar launch gaps beyond Character Builder

The 2026-05-16 broader audit added four pillars that are necessary for GhostRigger to feel like a complete KOTOR modding suite, not only a rigging window.

Research notes:

- [PyKotor's wiki](https://github-wiki-see.page/m/OldRepublicDevs/PyKotor/wiki) indexes the authoritative Aurora/KOTOR file specs for 2DA, GFF, ARE, IFO, ERF, KEY/BIF, LYT, VIS, WOK/BWM, and related resource formats.
- [KOTOR module structure](https://github-wiki-see.page/m/lachjames/KotOR-Modding-Guide/wiki/KotOR-Modding-101%3A-Introduction-to-Modding-for-KotOR-and-TSL) is split between static area models and instantiated templates; the [KOTOR Level Editor guide](https://github-wiki-see.page/m/lachjames/KotOR-Modding-Guide/wiki/KotOR-Level-Editor%3A-An-Introduction) maps cleanly onto GhostRigger's Module Editor vs Map Builder separation.
- Community notes on `.lyt`/`.vis` emphasize that LYT positions the AuroraBase of each room/model and VIS controls room visibility links.
- The [WOK format notes](https://kotor-modding.fandom.com/wiki/WOK_Format) confirm walkmesh face, adjacency, perimeter, and transition data that must be preserved when editing surfaces.

## Rules of engagement (unchanged from original)

1. **Qt-only.** No new Tk code accepted; CI guard via `test_qt_only_imports.py`.
2. **Spec-first.** When a UI question is ambiguous, defer to `knowledge_base/reference/specs/character_builder_spec.md` then to the AccuRig HUD reference.
3. **Stewart Jones is the creature playbook.** The 3-Stage Asset Build (Base / Animation / Deformation), the naming convention, the spline-IK / wing / tail rig structures, and the ROM test methodology are non-negotiable for Mode 4.
4. **Validation gates export** — Errors block, Warnings prompt.
5. **Commit per task ID.** Every commit message references its `T###` ID from this roadmap.
6. **PR per milestone**, not per task. Squash all task commits within a milestone into one comprehensive commit before opening the PR (the M5 pattern; see PR #53).
7. **No new runtime dependencies** beyond PySide6, numpy, moderngl, Pillow. Dev-only `pytest-qt` + `pytest-image-snapshot` permitted for M11.
8. **Standing legacy-UI retirement directive** — every milestone removes any legacy `Open … Panel…` placeholder it encounters.
9. **Never push directly to `main`.** Branch is `qt-ghostrigger`; PR target is `main` (which since PR #52, #53 advanced past the original `defe7f8` pin — current `main` is whatever `origin/main` reports at PR time).

## What we're *not* doing in this roadmap

- No new arbitrary autorig (generic non-KOTOR pipelines). Mode 4 covers what KOTOR creatures need; everything else is out of scope.
- No new LIP authoring tool (we preview, we don't author). LIPs come from the classic KOTOR pipeline.
- No new physics simulation beyond the existing cloth/dangly module + M8/T804 mandible preset.
- No swap to a different render backend (we extend `qt_viewport.py` + ModernGL + `viewport_core.py`, no PyOpenGL refactor).
- No music / sound design — `qt_animation_panel.py` already covers audio playback.
- No new runtime deps. `pygltflib`, `pyassimp`, `pyfbx` rejected — in-tree writers cover all four formats.
