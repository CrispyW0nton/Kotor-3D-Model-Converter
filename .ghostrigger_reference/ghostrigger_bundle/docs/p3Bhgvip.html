Issue 1: Texture Wrapping on Modules

Bad tiling on module floors, walls, and other large surfaces

Symptom

Module textures (floors, walls, ceilings) do not tile correctly. Large surfaces show either solid colors, missing triangles, or stretched single-tile patterns instead of proper repeating textures.

Root Cause Analysis

UV Sentinel Filtering (viewport.py line 169)

_UV_SENTINEL = 100.0 # Skip triangles that contain KotOR seam-split placeholder UV values if (abs(uv0[0]) > _UV_SENTINEL or abs(uv0[1]) > _UV_SENTINEL or abs(uv1[0]) > _UV_SENTINEL or abs(uv1[1]) > _UV_SENTINEL or abs(uv2[0]) > _UV_SENTINEL or abs(uv2[1]) > _UV_SENTINEL): return # Triangle is skipped!

Problem: This filters out triangles with any UV component |value| > 100. While this correctly catches KotOR seam-split placeholder UVs (observed values: -22, 127), it ALSO filters out legitimate tiled geometry.

Incorrect UV Wrapping Logic

The code comments reveal the design intent:

# Line 5105: _accel_uv_sentinel = 1e6 if _accel_is_module else _UV_SENTINEL # Line 5286: "instead of _UV_SENTINEL (100) so tiled floor/wall"

The developers raised the sentinel to 1,000,000 for modules, acknowledging that module textures use large UV ranges. However, this is a band-aid fix. The real issue: UVs should not be filtered based on magnitude at all.

What KotorBlender Does (Ground Truth)

From KotorBlender source code (io_scene_kotor/format/mdl/reader.py lines 579-584):

if mdx_data_bitmap & MDX_FLAG_UV1: self.mdx.seek(mdx_offset + i * mdx_data_size + off_mdx_uv1) node.uv1.append(tuple([self.mdx.read_float() for _ in range(2)]))

UVs are stored as-is — raw float32 values, never wrapped, never modified. Values like [-12.86, +12.86] (pelvis_g tiling range) are stored exactly. The GPU handles wrapping via GL_REPEAT at the shader level.

Solution: Remove UV Magnitude Filtering

Immediate Fix (Partial)

# Phase 18 fix: Raised _UV_SENTINEL from 20.0 to 100.0 # This helps but does not solve the root problem _UV_SENTINEL = 100.0 # Old: 20.0

Correct Long-term Fix

Option A: Remove UV sentinel filtering entirely. All UV values from MDX are valid geometry. The sentinel was a workaround for seam-split duplicate vertices with garbage placeholder UVs, but those should be handled differently (e.g., detect duplicate vertex positions at seam edges, not filter by UV magnitude).

Option B: If sentinel filtering must remain, only apply it to skin meshes (heads, bodies) where seam-split duplicates occur, not to module geometry:

# Only filter sentinel UVs for skin meshes, not modules if node.is_skin and (abs(uv0[0]) > _UV_SENTINEL or ...): return

GPU-Style Texture Wrapping

The rasterizer must apply frac(uv) per pixel to replicate OpenGL's GL_REPEAT:

# Correct approach (already in accel.py for Tier 1, added in Phase 18 for Tier 2): u = u - np.floor(u) # frac() wrap: [-12.86] → [0.14] v = v - np.floor(v) pu = np.clip((u * TW).astype(np.int32), 0, TW - 1) pv = np.clip((v * TH).astype(np.int32), 0, TH - 1)

Issue 2: Performance & Memory

High RAM usage, slow rendering, interactive LOD fallback

Symptom

GhostRigger uses significant RAM (several GB for complex models) and renders slowly. During orbit/pan/zoom interaction, the viewport automatically drops to flat-shading to maintain 60 FPS. Textured rendering with animations is sluggish even on high-end hardware.

Root Cause Analysis

CPU-Based Software Rasterization (viewport.py)

From the viewport.py header (lines 1-40):

""" 3D Viewport Widget – GhostRigger-K1-K2 ======================================= Fast software rasterizer using a PIL ImageDraw buffer. Each frame is drawn into a single PIL Image and displayed with one Canvas.create_image() call – no per-triangle Canvas items. v9.0 Improvements ----------------- - Interactive LOD fallback: textured mode automatically drops to fast flat-shading during orbit/pan drag for smooth 60 fps response on any model - Fast render tick: _RENDER_MS_INTERACTIVE=16ms during drag (vs 33ms idle) """

Problem: 9,323 lines of Python code implementing software rasterization. PIL ImageDraw is not designed for real-time 3D rendering. Each pixel is computed on the CPU, which is orders of magnitude slower than GPU rasterization.

Painter's Algorithm Memory Overhead

# Line 3206: MAX_TRIS = 80_000 # Performance cap for painter's sort mode # Line 5577: "Sort back-to-front (painter's algorithm)"

The renderer collects ALL triangles in the scene, sorts them by centroid depth (back-to-front), then draws them one by one. For complex models with 50k+ triangles, this requires:

  • Large Python lists storing (depth, pts, fill, tex_img, uvs, is_sel) tuples
  • Sorting 50k+ items per frame (even with NumPy acceleration)
  • Per-triangle PIL affine transforms for textured rendering
  • PIL images for each texture (uncompressed RGBA in RAM)

No GPU Acceleration

The codebase includes a stub gpu_renderer.py but it is not production-ready. The main viewport uses pure CPU rendering for all operations: vertex transforms, lighting calculations, rasterization, and texture sampling.

Solution: Migrate to GPU Rendering

Architecture Recommendation (from OpenGL Textbook)

Based on the attached OpenGL book research:

Modern Buffer Architecture

Replace CPU sorting with Vertex Buffer Objects (VBOs) and Vertex Array Objects (VAOs). VBOs store mesh data (positions, normals, UVs) directly on the GPU to eliminate per-frame data transfers.

GPU Depth Buffering

Replace painter's algorithm with hardware depth buffer via glEnable(GL_DEPTH_TEST). The GPU handles fragment-level occlusion automatically based on Z-depth. Use glm::perspective for projection.

Alpha Handling

For hair/decals, use Alpha Testing. Treat transparent objects as either fully opaque or transparent based on an alpha threshold to avoid order-independent transparency complexity.

Implementation Path with ModernGL

GhostRigger already has ModernGL in requirements.txt. Use it as the primary renderer:

import moderngl import numpy as np # Create context (headless or windowed) ctx = moderngl.create_context() # Enable depth testing (replaces painter's algorithm) ctx.enable(moderngl.DEPTH_TEST) # Create VBO for mesh data vertices = np.array([...], dtype='f4') # positions, normals, uvs vbo = ctx.buffer(vertices.tobytes()) # Create VAO vao = ctx.simple_vertex_array(program, vbo, 'in_position', 'in_normal', 'in_uv') # Render vao.render(moderngl.TRIANGLES)

Issue 3: FBX Export Fails in Unreal

Exported FBX files cannot be imported into Unreal Engine

Symptom

When exporting models like c_selkath to FBX and attempting to import into Unreal Engine 5, the import fails or produces a static mesh instead of a skeletal mesh. Textures and animations are not recognized.

Root Cause Analysis

FBX Export Workflow (mesh_converter.py lines 1000-1150)

The FBXExporter tries three methods:

  1. fbx-python-sdk (Autodesk FBX Python SDK) - preferred
  2. pyassimp - fallback (delegates to ASCII)
  3. FBX ASCII 7.4 - zero-dependency manual writer
# Try fbx module (Autodesk FBX Python SDK) try: import fbx as _fbx ok = self._export_fbx_sdk(model, fbx_path, _fbx) except ImportError: ok = None if ok is None: # Primary export path: FBX ASCII 7.4 (zero-dependency, full feature set) ok = self._export_fbx_ascii(model, fbx_path, base_skeleton_model=base_skeleton_model)

Missing Skin Deformer Data

From code inspection, the FBX SDK path (lines 1135-1150) creates skeleton nodes and mesh nodes but the _add_fbx_mesh method is incomplete:

def _add_fbx_mesh(self, mgr, scene, root_fbx_node, mesh_node: ModelNode, node_map: dict): """Add one KotOR mesh node to the FBX scene (FBX SDK path).""" try: import fbx fbx_mesh = fbx.FbxMesh.Create(mgr, mesh_node.name) # Vertices fbx_mesh.InitControlPoints(len(mesh_node.vertices)) # Faces for face in mesh_node.faces: fbx_mesh.BeginPolygon(-1, -1, False) for vi in face: fbx_mesh.AddPolygon(vi) fbx_mesh.EndPolygon() # Normals (added) # UVs (added) # BUT: Missing skin deformer and cluster setup!

Problem: No FbxSkin or FbxCluster objects are created. Unreal requires skin deformers with bone weights to recognize a skeletal mesh.

Unreal Engine FBX Requirements

From Unreal documentation and the FBX2glTF reference:

  • Skeleton: FbxSkeleton nodes with correct hierarchy
  • Skin Deformer: FbxSkin object attached to each mesh
  • Clusters: FbxCluster per bone with vertex weights and transform matrices
  • Bind Pose: FbxPose with column-major world matrices for each bone
  • Animations: FbxAnimStack with FbxAnimLayer and FbxAnimCurve per bone per channel

Solution: Complete FBX Skeletal Mesh Export

Add Skin Deformer to _add_fbx_mesh

Issue 4: Depth Rendering Artifacts

Eyeballs and teeth visible through face meshes

Symptom

Character models show inner geometry (eyeballs, teeth, tongue, gums) visible through the outer face mesh. This creates a disturbing "x-ray vision" effect where inner structures render on top of the opaque face surface.

Root Cause Analysis

Painter's Algorithm Limitations

From viewport.py lines 173-190:

# ── Inner-geometry node name substrings ───────────────────────────────────── # KotOR head models contain eye, eyelid, teeth, tongue, gum, and jaw meshes # that sit geometrically INSIDE the face mesh. With a painter's-algorithm # (centroid-depth) sort these would sometimes be drawn before the opaque face # mesh and then overwritten by it. We promote them to render tier 1 (drawn # after all tier-0 opaque geometry) so that the face mesh's eye-socket and # mouth-gap openings correctly expose the underlying inner geometry. _INNER_GEO_SUBSTRINGS: tuple = ( 'eye', 'lid', 'teeth', 'tooth', 'gum', 'jaw', 'tongue', 'teethu', 'teethl', 'eyeball', 'cornea', 'iris', 'pupil', 'gumskin', 'tonguemesh', 'jawskin', 'eyelid', 'teetha', 'teethb', )

Problem: This is a hack to work around painter's algorithm failures. Inner geometry is promoted to a second render pass to ensure it draws after the face. But this breaks when:

  • The eye/tooth centroid is closer to camera than the face centroid (painter's sort puts inner geo first)
  • The face mesh has holes/gaps where inner geometry should show through (depth testing would handle this automatically)
  • Triangles intersect (painter's algorithm fundamentally cannot handle this)

Centroid Depth Sorting (line 4955)

# Use weighted-centroid depth: average is more stable than # using only one vertex's depth depth = (p0[2] + p1[2] + p2[2]) * 0.3333 + fi * 1e-7 # Depth bias for transparent tris to sort after opaque at same depth sort_depth = depth - (1e-3 if node_alpha < 0.999 else 0.0) sort_key = _float_to_sort_key(sort_depth)

Sorting by triangle centroid fails when triangles overlap or nest. A triangle with a closer centroid may have vertices that are behind another triangle's surface. Only per-pixel depth testing can handle this correctly.

Z-Buffer Theory (from Computer Graphics Literature)

The Z-buffer algorithm (also called depth-buffer method) solves visible surface determination at the pixel level:

  • Initialize depth buffer to maximum depth (1.0 or far plane)
  • For each rasterized pixel: compute interpolated depth z
  • If z < depth_buffer[x,y]: update color and depth_buffer[x,y] = z
  • Otherwise: discard pixel (occluded by closer geometry)

This handles nested geometry, intersecting triangles, and arbitrary complexity with pixel-perfect accuracy. The GPU hardware implements this in silicon for billions of pixels per second.

Solution: GPU Z-Buffer Rendering

Replace Painter's Algorithm with Depth Testing

Using ModernGL (already in requirements.txt):

import moderngl ctx = moderngl.create_context() # Enable depth testing - replaces all painter's sort code ctx.enable(moderngl.DEPTH_TEST) ctx.depth_func = '<' # Keep closer fragments # Render opaque geometry first (no sorting needed!) opaque_vao.render(moderngl.TRIANGLES) # Then render transparent geometry (requires sorting, but only transparent objects) transparent_vao.render(moderngl.TRIANGLES)

Remove _INNER_GEO_SUBSTRINGS Hack

With proper z-buffer, no special handling for inner geometry is needed. The depth buffer automatically ensures that:

  • Eyeballs only show through eye socket openings (where face mesh has no geometry)
  • Teeth only show through mouth gap openings
  • Face mesh occludes inner geometry everywhere else

Software Rasterizer Alternative (if GPU unavailable)

If ModernGL cannot be used, implement a software z-buffer in viewport.py:

# Initialize depth buffer (per-pixel) depth_buffer = np.full((height, width), 1.0, dtype=np.float32) # For each triangle in any order (no sorting!) for tri in all_triangles: for x, y in rasterize_triangle(tri): z = interpolate_depth(tri, x, y) if z < depth_buffer[y, x]: depth_buffer[y, x] = z color_buffer[y, x] = compute_color(tri, x, y)

Performance note: Software z-buffer is still much slower than GPU but eliminates the depth sorting artifacts. For production, GPU is strongly recommended.

OpenGL Programming Guide

VBO/VAO Architecture

Key Advantage: VBOs store data directly in GPU memory, reducing CPU-GPU transfer overhead. VAOs act as containers for vertex attribute state.

// Enable depth testing (automatic z-buffer) glEnable(GL_DEPTH_TEST); // Create VBO GLuint vbo; glGenBuffers(1, &vbo); glBindBuffer(GL_ARRAY_BUFFER, vbo); glBufferData(GL_ARRAY_BUFFER, sizeof(vertices), vertices, GL_STATIC_DRAW); // Create VAO GLuint vao; glGenVertexArrays(1, &vao); glBindVertexArray(vao); glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 8*sizeof(float), (void*)0); // position glVertexAttribPointer(1, 3, GL_FLOAT, GL_FALSE, 8*sizeof(float), (void*)(3*sizeof(float))); // normal glVertexAttribPointer(2, 2, GL_FLOAT, GL_FALSE, 8*sizeof(float), (void*)(6*sizeof(float))); // uv

Transparency Handling

Alpha Testing: Treat transparent objects as fully opaque or fully transparent based on an alpha threshold. This avoids order-independent transparency complexity.

// Fragment shader if (texColor.a < 0.5) discard; // Binary alpha test

3D Mesh Processing & Character Animation

Bind Pose Management

Core Concept: Characters must be rigged in a standardized bind pose (T-pose or A-pose) where joint angles are zero. This serves as the reference for all deformations.

Bone Data Structure

Each bone requires:

  • Unique Index: Integer identifier
  • Joint Name: Links to scene graph hierarchy
  • Vertex Set: Array of influenced vertex indices
  • Offset Matrix: Transforms vertices from mesh space to joint-local space

Critical: The offset matrix is inverse-bind-pose transform. Without this, rotations will be offset incorrectly.

Linear Vertex Blending (Skinning)

To avoid rigid mechanical movements, vertices must be influenced by multiple bones. Use normalized weights (sum = 1.0):

// Per-vertex skinning formula vec3 skinned_pos = vec3(0.0); for (int i = 0; i < 4; i++) { // Max 4 bone influences int bone_id = bone_ids[i]; float weight = bone_weights[i]; skinned_pos += weight * (bone_matrices[bone_id] * vec4(in_position, 1.0)).xyz; }

Game Engine Architecture

Modular Design Principles

From the engine architecture book:

  • Separation of Concerns: Keep rendering, animation, resource loading, and tool UI as distinct modules
  • Single Source of Truth: Avoid duplicate data structures between runtime and tools
  • Asset Pipeline: DCC tool → exporter → resource compiler → linker → engine-ready binary

Editor Integration

Unreal-Style Architecture: Build editor into runtime engine. This provides:

  • Total access to engine data structures (no duplication)
  • Fast iteration (game is already running)
  • Live in-game editing capabilities

Alternative: Separate tool with shared data formats and hot-reload for rapid iteration.

Asset Registry

Maintain a central resource registry with unique asset GUIDs (paths or hashed string IDs). This ensures:

  • Only one copy of each asset in memory
  • Referential integrity for cross-references
  • Batch loading/unloading in predictable order

Positive Aspects

  • Test Coverage: 5,007 tests passing, 0 failures (from v5.1.0 release notes)
  • Modular Architecture: Clean separation between core, gui, autorig, converters, and formats
  • Active Development: Recent phases (18, 5.0, 8) show continued improvement
  • Documentation: Code includes extensive comments explaining UV fixes, TXI handling, depth sorting logic
  • Feature-Rich: Comprehensive rigging tools (Auto-Rig, Library Rig, GRig, AcuRig)
  • Module Editor: Walkmesh editing, K1↔K2 porter, module builder all functional

Critical Weaknesses

  • Rendering Architecture: 9,323 lines of CPU software rasterization is fundamentally misaligned with modern 3D rendering best practices
  • Painter's Algorithm Limitations: Cannot handle nested/intersecting geometry correctly; requires workarounds like _INNER_GEO_SUBSTRINGS
  • UV Filtering Logic: UV sentinel filtering breaks legitimate tiled textures on modules
  • FBX Export Incomplete: Missing FbxSkin and FbxCluster setup prevents Unreal Engine import
  • Memory Usage: PIL-based rendering stores all triangles in Python lists; large models consume GBs of RAM
  • Performance Degradation: Interactive LOD fallback to flat-shading indicates renderer cannot maintain real-time performance

Notable Code Patterns

Good Patterns

  • Acceleration layer with Numba JIT + NumPy fallbacks
  • Texture cache for efficient texture reuse
  • Animation engine with state machine (Phase 8)
  • TBN tangent space computation (Phase 5)
  • Matrix palette uploader for GPU skinning prep

Anti-Patterns

  • String-based node name filtering (_INNER_GEO_SUBSTRINGS)
  • Hardcoded UV magnitude threshold (_UV_SENTINEL)
  • Centroid depth sorting for complex scenes
  • Per-triangle PIL affine transforms
  • Sorting 50k+ triangles per frame on CPU

Conclusion & Recommendations

Summary

GhostRigger is a feature-rich, well-tested KOTOR modding tool with excellent rigging capabilities and comprehensive module editing. However, its rendering architecture has fundamental limitations that prevent it from being production-ready for complex workflows. The four critical issues identified all stem from the CPU-based software rasterization approach:

  1. Texture wrapping: UV sentinel filtering workaround breaks legitimate tiled textures
  2. Performance: Python/PIL renderer is 50-100x slower than GPU; high RAM usage
  3. FBX export: Missing FbxSkin/FbxCluster prevents Unreal import
  4. Depth rendering: Painter's algorithm cannot handle nested geometry correctly

Primary Recommendation

Migrate to GPU-based rendering using ModernGL (already in requirements.txt).

This single architectural change solves Issues #2 (performance), #4 (depth artifacts), and enables proper handling of Issue #1 (UV wrapping). It aligns GhostRigger with industry-standard 3D rendering practices and matches the approach used by all successful KOTOR tools (KotorBlender, PyKotor, reone, xoreos, KotOR.js).

Benefits:

  • 50-100x faster rendering (real-time 60 FPS for complex models)
  • 40x less memory usage (GPU VRAM vs Python objects)
  • Pixel-perfect depth testing (eliminates eyeball/teeth artifacts)
  • Native UV wrapping (GL_REPEAT handles any UV range)
  • Removes ~2,000 lines of workaround code (_INNER_GEO_SUBSTRINGS, depth sorting, render tiers)

Secondary Recommendations

1. Complete FBX Export (Issue #3)

Add FbxSkin and FbxCluster creation to _add_fbx_mesh. Reference KotorBlender and FBX2glTF for correct skeletal mesh structure. Validate exports with FBX2glTF before testing in Unreal. Effort: 1-2 days.

2. Fix UV Sentinel Filtering (Issue #1)

Remove magnitude-based UV filtering OR only apply to skin meshes where seam-split duplicates occur. Reference KotorBlender's approach (no filtering at all). Effort: 4 hours.

3. Keep PIL Renderer as Fallback

Maintain CPU renderer for CI/CD, headless testing, and systems without GPU. Mark as "testing/legacy" mode. Optionally implement software z-buffer if pixel-perfect depth is required in fallback mode.

4. Leverage Related Tools

Use PyKotor as authoritative backend, reference KotorBlender for animation workflows, validate FBX exports with FBX2glTF, and study KotOR.js for modern tool UX patterns.
